# 🧪 Mighty Skill-Bridge: UAT テスト仕様書 (UAT_TEST_SPECIFICATION)

> **人間が手順どおりに実行し、OK / NG を判断できる**受入テスト（UAT）仕様書。
> T845「全機能本番受入E2E/UAT最終再検証」の**手動実行の正本**として使用する。自動E2E（アプリ層）は T845_1（`scripts/run_ga_acceptance_e2e.py`）が担保し、本書は人間が本番相当環境で最終確認する範囲を定義する。
>
> 本書の完全性・整合性は [`scripts/audit_uat_test_spec.py`](../scripts/audit_uat_test_spec.py)（10仮説）と `tests/test_uat_test_spec.py` が CI で継続検証する（各ケースの必須項目・OK/NG判定・実在WBS/API参照・ドメイン網羅）。

---

## 1. 目的と対象範囲

- **目的**: 社内GA対象機能が本番相当環境で仕様どおり動作することを、人間が再現可能な手順で確認し、合否（OK/NG）を記録する。
- **対象範囲**: 適性アンケート / 勤怠 / 営業メールAIマッチング / 管理者ダッシュボード / 法定同意ゲート / データエクスポート・削除 / サポート / フィードバック・NPS / ライトモード / ヘルスチェック・公開デモ / レートリミット。
- **対象外**: 有償課金の live 実行（T862 判断後）、外部メール実接続の実データ（T836 受領後）。これらは該当WBSのゲートで別途実施する。

## 2. 事前準備（テスト環境・認証・データ）

| 項目 | 内容 |
| :--- | :--- |
| 本番URL | `https://mightylink-app.com/` および Firebase Hosting 既定URL |
| 認証 | Firebase Auth（保護APIは ID トークン検証。テストは Auth Emulator またはテスト用アカウントで実施）。公式: ID トークンは Admin SDK で検証、認証保護フローは Auth Emulator でテスト（Firebase Auth docs 2026-07-03 確認） |
| 管理者API | Basic 認証（`BASIC_AUTH` 環境変数）。テスト実施者は管理者資格情報を安全経路で受領する |
| データ確認 | Supabase（本番 PostgreSQL 17.6・RLS 有効）。保存確認は管理者集計API または運用者のSQL確認で行う |
| テストデータ | 個人情報を含まない合成データ（サンプル経歴書/案件票、合成勤務表 CSV/Excel）を使用する |
| 同意バージョン | 診断系APIは `LEGAL_CONSENT_VERSION = MSB-LEGAL-2026-06-DRAFT` の同意を必須とする |

## 3. 判定の凡例

- **OK**: 「OK判定」に記載した条件を**すべて**満たす。
- **NG**: 「NG判定」に記載した事象が**一つでも**発生する。
- **N/A**: 前提条件を満たせずテスト不能（理由を備考に記載）。

各ケースの「実施結果」欄に OK / NG を記入し、実施日・実施者・備考を残すこと。NG は課題管理表（`data/issues_tracker.tsv`）へ起票する。

> **⚠️ 同意・必須項目ゲートを検証する際の注記（重要）**
> ブラウザの HTML5 必須検証は、フォーム内で **DOM 順に最初に見つかった空の必須項目**でエラーを表示して停止する。したがって、ある特定のゲート（例: 同意チェック）だけを検証したい場合は、**それ以外の必須項目を先にすべて入力**し、検証したい項目だけを空/未入力にすること。さもないと別の空欄（例: 社内確認コード）でブロックされ、目的のゲートを検証できない（＝その手順は OK ではなく **N/A** とし、条件を整えて再実行する）。
> また、クライアント側検証は DevTools 等で回避可能なため、重要なゲート（同意・認証）は**サーバー側の拒否（HTTP 400/401 等）**も併せて確認する。

### TS-01 適性アンケートの同意必須送信
- **対象機能**: 社内適性・状況アンケート（同意ゲート）
- **関連WBS**: T840
- **関連API**: POST /api/employee-assessment/responses
- **前提条件**: 本番URLにアクセスでき、社内確認コードを保有している。個人情報を含まない合成回答を用意する。フォームの必須項目は「社内確認コード（3文字以上）」「部署カテゴリ」「フリー記述（**10文字以上**、サーバー検証あり）」「同意チェック」の4つ（いずれも HTML5 `required`）。※同意ゲートを切り分けるため、同意以外の必須項目は先に埋めること（§3 の注記参照）。
- **テスト手順**:
  1. ホーム画面のアンケートセクションを開く。
  2. **同意チェック以外の必須項目**（社内確認コード・部署カテゴリ・**フリー記述は10文字以上**）をすべて入力し、motivation/culture を選択し、**同意チェックだけを外したまま**「送信」する。
  3. 同意チェックも入れて（全項目入力の状態で）送信する。
  4. （サーバー側検証）DevTools 等でクライアント検証を回避し、`consented=false` のまま `POST /api/employee-assessment/responses` を送信する。
  5. フリー記述を9文字以下（例「テスト」）にして送信し、UI のエラーメッセージを確認する。
- **期待結果**: 手順2はブラウザが**同意チェックボックス**で「このチェックボックスをオンにしてください」と表示し送信不可（`未送信`のまま）。手順3は成功表示と `response_id`（1以上）が返る。手順4はサーバーが HTTP 400（`consent is required before storing the response`）で拒否する。手順5は UI が理由（「フリー記述は10文字以上で入力してください」等の具体的メッセージ）を表示する（「接続できませんでした」等の誤表示は NG）。
- **OK判定**: 手順2で**同意チェックボックス**を理由に送信拒否、手順3で成功し `response_id` が返る、手順4でサーバーが 400 拒否、手順5で UI が具体的な理由を表示、の4点をすべて満たす。
- **NG判定**: 同意なしでクライアントまたはサーバーが保存を受理する／全項目＋同意ありかつフリー記述10文字以上で 400・500 になる／手順2のブロック理由が同意以外の項目（例: 社内確認コード）になり同意ゲートを検証できない／手順5で「接続できませんでした」等、実際の 400 理由を隠す誤表示になる。
- **実施結果**: ☐ OK　☐ NG　／　実施日: ______　実施者: ______　備考: ______
