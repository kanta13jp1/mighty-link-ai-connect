## 0. これは何の作業ですか（30秒サマリー）

サービスの**インターネット上の住所（URL）を、正式なものに整える**作業です。

- これまで: `mighty-link-ai-connect-13d22.web.app`（Google から借りた仮の住所。長くて覚えにくい）
- これから: **`https://mightylink-app.com/`**（自社で取得した正式な住所。短く、サービス名がそのまま読める）

サービスの中身（プログラム・データ）は一切変わりません。**お客様から見える入口（看板と住所）を、正式なものに掛け替えるだけ**です。

---

## 1. なぜこの作業が必要なのか（ビジネス上の理由）

| 理由 | 説明 |
| --- | --- |
| **信頼性** | お客様に「web.app」という借り物の住所を案内するより、自社ドメインの方が圧倒的に信頼される |
| **有料化の前提条件** | クレジットカード決済（Stripe）の審査では、「特定商取引法に基づく表記」のページが**自社の正式 URL で公開されていること**が求められる。この住所整備が終わらないと、**課金サービスを開始できない** |
| **ローンチ日程** | 正式リリース告知の前に、法定ページ公開 → 決済審査 → 課金テスト の順で進む必要があり、**この作業がその一番手前**にある |

---

## 2. なぜ会社ドメインを使わなかったのか（重要な判断）

当初は会社ドメイン **ml-mightylink.com** の一部（`app.ml-mightylink.com`）を本番 URL にする計画でした。しかし、設定に必要な「住所録（DNS）」の**管理アカウントが社内で特定できませんでした**。

- ml-mightylink.com は 2026年4月1日に「Squarespace」というサービスで登録されている
- その住所録は Google のシステム上に存在し、**会社のホームページとメールはそこで動いている**
- ところが、梅澤の個人アカウントと業務アカウント（k-umezawa@ml-mightylink.com）の**両方を機械的に全件調査しても、その住所録は見つからなかった**（＝ドメインを登録した第三者のアカウントにある）

会社のホームページ・メールが動いている住所録を不用意に触ると、**メールやサイトが止まるリスク**があります。そこで、**サービス専用の新しいドメイン（mightylink-app.com）を自社で新規取得**し、自分たちだけで完結して管理する方針に切り替えました。

> この判断は課題管理表 **R54** に記録済み。会社ドメインの管理者が将来判明すれば、`app.ml-mightylink.com` を別名として追加することも可能で、今回の対応と両立します。

## 3. 何をしたか（作業の流れ）

専門的に見えますが、やったことは「**住所を1つ買って、サービスにつなぐための情報を住所録に書いた**」だけです。

| # | 作業 | 例えると | 担当 |
| --- | --- | --- | --- |
| 1 | お名前.com で `mightylink-app.com` を登録 | 住所（土地）を買う | 社長/担当 |
| 2 | 住所録に2つの情報を登録（下表） | 「この住所に来たら、ここに案内して」と書く | 担当 |
| 3 | 住所録の参照先を切り替え（ネームサーバー変更） | 「世界中の郵便局はこの住所録を見て」と宣言 | 担当 |
| 4 | Firebase で所有権を確認 → SSL 証明書 自動発行 | 鍵付きの安全な通信を有効化 | 自動 |

### 住所録に登録した2つの情報

| 種類 | 役割（例え） | 値 |
| --- | --- | --- |
| **A レコード** | 「この住所の実際の案内先（番地）」 | `199.36.158.100`（Firebase の配信先） |
| **TXT レコード** | 「この住所は確かに私たちのもの、という合言葉」 | `hosting-site=mighty-link-ai-connect-13d22` |

## 付録 B: よくあるトラブルと対処

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| Firebase が「DNS リクエストが失敗しました」と出続ける（公開DNSは正しいのに） | **Firebase の確認システム内部のDNSキャッシュ**が、ネームサーバー切替前の古い情報（駐車場）を保持中。一般の公開DNS（Google/Cloudflare）より更新が遅く、**最大24〜48時間**かかることがある | **待つのが正解**。設定変更・削除再登録・確認連打は不要（早まらない）。Firebase が保留中ドメインを自動再確認し、内部キャッシュ更新後にひとりでに「接続済み」になる。多くは数時間で完了 |
| 公開DNSでは正しい値が見えるのに Firebase だけ失敗する | 上と同じ（Firebase 内部キャッシュのラグ）。`mightylink-app.com` への通信自体は既に Firebase へ到達しており、証明書発行待ちの状態 | 同上（自動完了を待つ） |
| 住所録に書いた値が反映されない | ネームサーバーが dnsv.jp に切り替わっていない | お名前.com「ネームサーバーの設定」で「お名前.comのネームサーバーを使う」（= 01〜04.dnsv.jp）を選択 |
| ある日突然サイトに繋がらなくなった | ドメインの更新期限切れ | お名前.com で更新。自動更新の有効化を推奨 |

> **2026-06-13 時点の状況**: DNS 設定（A/TXT/ネームサーバー）は完了し、登録局・公開DNS すべてで正しい値を確認済み。`mightylink-app.com` への通信も Firebase へ到達済み。残るは Firebase 内部キャッシュの自動更新（最大24時間目安）→ 完了後に SSL 自動発行され「接続済み」になる。**人手の作業は完了しており、自動完了待ちの状態**。
